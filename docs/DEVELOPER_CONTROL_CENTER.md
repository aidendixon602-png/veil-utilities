# Developer control center: implementation status

## Audit and prioritized plan

1. Restrict all existing dashboard routes and saves to Veil developers, recheck Discord-discovered identities, revoke sessions on logout/restart, and retain OAuth, CSRF and HTTPS protections. Do not alter bot command permissions.
2. Reorganize navigation and present real bot/server information; preserve the server feature, Roblox group and authorization workflows.
3. Add bounded, read-only views of existing moderation cases and security incident records. Avoid rendering arbitrary reason/details fields and credentials.
4. Expand only after identifying shared, authorized backend services, adding audit/confirmation/state rechecks and testing partial failures. Do not simulate unimplemented monitoring, recovery or destructive operations.

The existing UI is server-rendered `aiohttp`, with embedded CSS and a small same-origin JS file; there is no frontend framework or WebSocket route. Routes and OAuth/session logic are in `core/dashboard.py`, forms in `core/dashboard_features.py`, the public Roblox lookup in `core/dashboard_roblox.py`, and data in the existing `core/db.py` SQLite/PostgreSQL adapters. The bot's developer identities are configured `OWNER_IDS`, built-in `BOT_DEVELOPERS`, and the Discord application owner/accepted team. The dashboard does not use server ownership, Discord Administrator, Veil ranks, fake permissions, or Antinuke trust to authorize access.

## Changes and limits

The overview reports gateway readiness, process uptime, joined and authorized server counts, and open/containing incident *records*, where available; none is a guarantee of service health or ongoing attacks. The searchable server inventory and existing settings pages remain. The control center links to real per-server security, logging and Roblox settings. Moderation shows 25 cases per page, selected by joined server; incident records show the latest 25 for the selected server. Case reasons and incident details are omitted, not exposed in raw logs. Database status is only a `SELECT 1` query, and the cog list is the bot's current in-process view.

This is **not the complete requested rebuild**. Missing features include Roblox monitoring, raid detection, lockdown, snapshots, comparisons, scheduling and recovery; searchable/paginated full logs; moderation actions/history beyond stored cases; API health probes; backup/restore controls; remote session management; cross-server operations; a comprehensive durable dashboard audit history; and the requested complete design/accessibility and mobile/browser validation. Roblox Open Cloud credentials are host environment secrets, not dashboard/database entries; encrypted credential storage in the dashboard is not implemented. Unknown/unavailable status is not represented as healthy, and no unsupported action is offered. The incident store is not necessarily a complete history of all security events. Existing Antinuke remains best effort and restoration can be incomplete.

The existing OAuth protocol is unchanged, but old sessions are invalidated. New sessions use an in-memory registry and last 12 hours. Logout invalidates that session in this process; restart invalidates all sessions. There is no multi-process or durable session revocation. Every request rechecks developer access, and existing saves recheck immediately before writing. Rate limits are process-local, bounded and use the TCP peer (anonymous) or session user ID; all visitors behind a common proxy can share one anonymous bucket. They do not replace upstream rate limiting or a shared session store. Dashboard request logging avoids URLs, request data, credentials and OAuth codes; host-level access logs and proxy configuration must be reviewed separately. Existing dashboard save locks are process-local and are not cross-process compare-and-swap; uncertain database outcomes require review before retrying.

Roll back by disabling `DASHBOARD_ENABLED` or deploying the previously verified version through the normal operator process. Rolling back restores the *previous owner/developer dashboard access policy*, so disable the dashboard until the previous behavior is explicitly reviewed. The Roblox role action journal is created automatically; rolling back leaves that table in place. Do not restart/deploy production without authorization; set `AUTO_SYNC_GIT=0` in the process environment before starting a local bot. Live Discord OAuth, real Roblox API connectivity, production data and browser layouts have not been tested by these changes.

The developer-only cases include denied server owners and nondevelopers, accepted versus invited team members, stale cookies, revocation, CSRF and server-scoped case access.

Existing failures are primarily logging, dashboard logging and strip-card tests and remain unresolved. ## Roblox member role controls

This is a deliberately limited integration, not the full Roblox Security module. A developer can enter a Roblox **numeric user ID** and a role ID, review current role IDs and the target role, and separately assign or remove that one role. Public role IDs are listed on the group page when Roblox provides them. Roblox supports multiple roles; assigning one does **not** replace another. Review role permissions in Roblox before confirmation. There is no automatic promotion/demotion workflow, member removal, join-request management, bulk operation, monitoring, lockdown, backup or recovery.

### Host setup

1. Through Roblox Creator Hub, create a least-privilege Open Cloud API key for the intended group, with `group:read` and `group:write` permissions for the groups API, and restrict IP addresses if supported. Its owner must have appropriate Roblox group privileges and hierarchy; Roblox can still deny actions. Follow [Roblox API key guidance](https://create.roblox.com/docs/cloud/open-cloud/api-keys). Never use a `.ROBLOSECURITY` cookie or paste secrets in dashboard fields, chat, source control or logs.
2. Set `ROBLOX_OPEN_CLOUD_GROUP_ID` to that one group’s positive numeric ID and `ROBLOX_OPEN_CLOUD_API_KEY` to the key in the host's protected secret/environment configuration. This deployment supports **one** Open Cloud group credential, not one per Discord server. Any developer-accessible server connected to that exact group can use the same credential; treat that as shared authority and select group IDs carefully. A saved group ID alone grants no Roblox authorization.
3. After an authorized normal deployment/restart, connect the same group ID in the developer-only dashboard. The key is read at process start and never displayed or stored in the database. Removing either environment value disables writes after restart; revoke the key in Roblox for immediate upstream invalidation. Never restart production without authorization. Set `AUTO_SYNC_GIT=0` in the process environment before starting the bot.

The API is beta and can change. Membership lookup requires the current complete `roles` array; missing, ambiguous or malformed data fails closed. Endpoints use a fixed Roblox host, a timeout, bounded uncompressed JSON, no redirects and no automatic retries. HTTP/API availability, credential scope, group ownership and hierarchy affect success. No live Open Cloud testing has been performed.

The review expires after five minutes, is session- and server-bound and can be used once. CSRF/origin checks, developer access and group settings are rechecked, as are the current membership and target role. Locks and reviews are process-local; other processes or Roblox actions can race after the recheck, and there is no atomic compare-and-swap or rollback. The action journal records request ID, actor, group, user, role, operation, time and outcome; it is not a complete Roblox audit trail. A `pending` or `unknown` outcome can mean the change occurred even if no response was received: inspect the member in Roblox and investigate before any retry. The dashboard does not retry. Journal retention follows normal database retention; restrict database access and backups. Restoring an old database can lose recent audit history.

Rollback: revoke the key in Roblox and remove the host environment variables; disable the dashboard or deploy a reviewed prior version through the normal authorized process. The `roblox_role_actions` table persists and can be retained for audit or removed through reviewed database administration. A rollback to a version before developer-only policy may restore owner access, so disable the dashboard until its access policy is reviewed.
